# VisualBoyAdvance .sgm states

**Status:** local next build supports narrowly scoped raw party-record recovery for selected VBA 8/9 games; conditional PK6 export; no PC support. Two supplied old states were gzip-compressed VisualBoyAdvance version 8 snapshots; decompression yielded 740,238 bytes in the tested cases. Neither an extension nor gzip alone identifies the game or a supported layout.

The old serialization stores IWRAM beginning at decompressed offset `0x1DF` for these particular states. A Ruby-specific probe found a player party at IWRAM `0x03004360` (file offset `0x453F`) and an opponent party at `0x479F`. Both locations can contain plausible Pokémon: distinguishing player ownership and validating record checksums matters. The user's other state identifies a different game; its species numbering cannot be assumed to be Ruby's. These offsets are evidence for the observed version and builds, not a general VBA specification.

The local research utility lives outside this web repository at `misc-save-recovery/Probe/Program.cs`. That earlier utility did not by itself establish Liquid Crystal or Dark Rising support; see the subsequently validated readers below. [VBA-M GBA state source](https://github.com/visualboyadvance-m/visualboyadvance-m/blob/master/src/core/gba/gba.cpp) is useful background, but a different version may serialize fields differently. Add per-version fixtures, RAM-address discovery, malformed input tests and explicit game identification before expanding browser support to additional revisions. Conversions require the relevant source species, ball, shiny and location mappings, which are not derivable from the container itself.

## Local browser implementation

[VbaParty.cs](../../src/PKHeX.Everywhere.RomHacks/Historic/VbaParty.cs) limits gzip expansion, accepts exact known version-dependent lengths, checks the 16-byte header and explicit user-selected revision, and reads the party count before validating each 100-byte record. Version 8 and 9 IWRAM begin at `0x1DF` and `0x1E5`; palette RAM occupies `0x400` bytes between IWRAM and EWRAM. FireRed-derived examples use EWRAM party count `0x02024029` and player party `0x02024284`; the supplied Emerald-derived Liquid Ocean example uses `0x020244E9` and `0x020244EC`. Opponent arrays are separate. These addresses are not guaranteed by a shared ROM header; a different hack can share it and have another layout.

The selected ROM's offline-derived name/ID allowlist admits only official-name matches at the usual native species ID. Unknown/custom species are skipped; names do not prove unchanged forms or mechanics. The reader can produce PK6 files for non-egg records whose species, moves and held items have matching source names and whose ball is the observed standard Poké Ball. Native records and metadata accompany the output. The export keeps trainer, moves, IVs and EVs, but marks the met location unknown and uses standard ability and PID-derived shiny assumptions; it may adjust PID to prevent a Gen 3 non-shiny becoming shiny under later thresholds. Source ID, PID, met location and original bytes are retained. Name matches do not establish identical mechanics or legal encounters. Six actual user states from four profiles and synthetic corruption/unmapped tests passed; source states stay private. More revisions, boxes, custom ID/ball/location conversions, and VBA versions need independent evidence. See the relevant hack notes.

Local experimental support now also reads both live party and pointed PC storage for the specifically selected 2012 Liquid Crystal and 2013 Dark Rising ROM revisions in VBA 9 states. Twelve supplied states were parsed; one matching Dark Rising battery snapshot and the Liquid Crystal partial battery's party/PC bytes independently corroborated the latest states. Shared FireRed headers cannot identify the exact ROM: the user must choose it. The PK6 conversion is approximate and original fields/records are retained; see the individual game notes.
