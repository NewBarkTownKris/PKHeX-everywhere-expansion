# Rijon Adventures — limited VBA party research

**Status:** local next-build, read-only native party-record recovery from explicitly selected revisions only; conditional PK6 export; no PC extraction or battery-save adapter. Two supplied revisions and VBA states: the 16 MiB FireRed-header revision (VBA 8) and the 2009 Beta (VBA 9) each contain one checksum-valid player party record; opponent records occupy a different array. ROM headers are different in these samples, but the ordinary FireRed header is shared and cannot uniquely identify a hack.

ROM SHA-256 fingerprint(s): `848c7169f005fae5e9ff9ab437b2896bcbdfd875862d28ed2a32a85595ea646d`, `592dc0caa5f77a798569d92d95a1ff64ac0f58a30f6ae10d7c9060b7287ba2c5`. Source species name tables and their conservative derived allowlists: [rijon](../../src/PKHeX.Everywhere.RomHacks/Historic/vba-rijon.json), [rijon-2009](../../src/PKHeX.Everywhere.RomHacks/Historic/vba-rijon-2009.json). The allowlist requires the same official name and original Generation III internal species ID. Unmatched IDs, including custom species, are skipped. Name/ID agreement is necessary evidence, not proof of unchanged stats, forms, abilities or evolution semantics; the ROM header in a state cannot establish the exact matching ROM.

The [VBA reader](../../src/PKHeX.Everywhere.RomHacks/Historic/VbaParty.cs) validates version, length, game header, party count and Gen 3 record checksums. Its native `.bin` records retain the original OT, ball, shiny-related PID/OT, moves and met fields; these fields are retained in metadata; eligible records can additionally export to PK6 with an unknown met location and standard ability/shiny assumptions. Species, moves and items use conservative name matches, not proof of matching mechanics. Only standard Poké Balls are presently accepted for portable export. Game-specific ball, shiny, item, move and location behavior has not been verified. Do not assign standard routes or portable origins merely from numeric ID. The party must be independently checked against real gameplay and future tests must include boxed Pokémon and more species.

See [VBA state research](../formats/vba-sgm.md) and [the synthetic checks](../../src/PKHeX.Everywhere.ProfileChecks/VbaChecks.cs). Private supplied states are not in this repository.

## Source location investigation

Both ROMs contain a candidate FireRed-style map-name pointer table at file offset `0x3F1CAC`, with pointer references at `0xC0C94` and `0xC4DB8`. For the supplied states, native met ID 88 is named **Gravel Town** in both tables; a generic FireRed interpretation would display Pallet Town. Of 109 candidate entries, 75 match retail names at the same ID in the earlier ROM and only 14 match in the 2009 Beta (case/punctuation normalized). These are table-name observations, not verified game lookup or region assignments. Portable files continue to mark locations unknown. The local audit files and generator stay outside the repository pending validation.

## Rijon Adventures 2009 Beta — local selected save and mGBA recovery

The exact supplied 2009 Beta ROM (`592dc0caa5f7…`, CRC `935ECB8B`) now also has selected FireRed-layout battery and exact-build mGBA version 7 party/PC PK6 export. A Gary Edition Eevee was seeded into this revision, displayed in its party screen, re-saved in mGBA and reopened; original party bytes and PK6 identity, OT and moves agree. This is not a Pokémon independently caught in Rijon. Real PC contents and further species/mechanics remain unverified; PC and invalid pointer coverage are synthetic. Earlier VBA 9 party recovery remains separate. Its map table uses native ID 88 for Gravel Town rather than Pallet Town, so source locations remain unknown in portable output; raw IDs are preserved. See the earlier mapping and limitations above. The different supplied Rijon revision is not covered by this new battery/mGBA profile.

## Older Rijon mGBA state recovery

The supplied older ROM’s exact CRC is `F57EC245`. Its existing VBA 8 party reader now also supports mGBA version 7 states from that exact ROM, using the same FireRed-layout party and PC addresses. A native party Pokémon from the supplied VBA state was inserted into an isolated mGBA game checkpoint and displayed correctly in the game’s party screen. Its native party record matched the VBA source byte-for-byte and its PK6 identity passed. This is a seeded fixture; occupied PC records are synthetic-only, and a natively obtained mGBA Pokémon has not been tested.

A fresh in-game battery save failed in mGBA, including when FLASH1M was forced on a fresh boot. The supplied VBA state does not contain a complete Flash save. A matching game-created battery save was unavailable; this is not a fakemon exclusion. The 2009 Beta is a separate revision.

A private battery fixture was subsequently reconstructed from the supplied VBA state’s live SaveBlock1, SaveBlock2, party and PC memory using standard FireRed sector layout and checksums. The experimental selected battery reader recovered the original party record byte-for-byte and produced the same PK6. The matching ROM displayed its continue/recap, but did not reach a stable playable scene from this reconstructed fixture, and writing a fresh in-game battery save failed. Therefore this is **reconstructed-memory and synthetic PC evidence only**, not independent validation against a game-created save. The original VBA file was unchanged; the reconstructed save is for research only. The reader requires complete valid sectors and displays this limitation.
